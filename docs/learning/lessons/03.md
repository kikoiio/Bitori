# 第 03 课：Agent Loop 与 Plan Mode

- 前置：第 02 课。
- 结果：用户发送一次任务，Bitori 自主完成多轮模型请求、工具执行与结果回写，并支持 PLAN/DO 模式。
- 预计：9-11 小时。
- 环境：同第 02 课；真实验收需要一个可用的兼容 profile。

## 1. 为什么学这一课

固定两阶段工具流程无法完成“先查文件、再改文件、最后跑验证”的任务。Agent Loop 把模型迭代抽成独立系统，同时必须避免无限循环、丢失状态和无法取消。本课的难点是事件顺序与持久化，而不是新增工具。

## 2. 能力规格

- 一次用户消息自动重复“请求模型、执行工具、回写结果”，直到模型不再请求工具。
- 每次模型迭代形成独立助手消息；单任务最多 20 次迭代。
- 连续三轮全部请求未知工具时停止，并写明原因。
- 取消保留已完成内容；模型流错误保存部分内容和实际用量。
- `/plan` 不请求模型，PLAN 只公开读取工具；写入和命令在审批前被结构化拦截。
- 最近自然完成的计划按会话保存；`/do` 切回 DO 并立即执行。
- 模式、计划、消息、工具结果、停止原因和逐轮/累计用量持久化；恢复现场但不自动续跑。
- 连续只读并发；写入和命令保持串行屏障并逐项审批。

## 3. 代码走读

1. `src/agent/runner.ts`：迭代、上限、停止语义。
2. `src/agent/stream-collector.ts`：单次流消费与工具参数组装。
3. `src/agent/safety-batch-scheduler.ts`：并发读取段与副作用屏障。
4. `src/agent/context.ts`：user、assistant tool call、tool result 的协议顺序。
5. `src/chat/agent-event-projector.ts`：顺序落盘与状态投影。
6. `src/chat/agent-controller.ts`：命令、会话与取消。
7. 存储迁移版本 3 与恢复逻辑。

## 6. 常见卡点

- 工具开始前迭代未落盘：依赖事件投影背压，不要绕过队列直接改 UI 状态。
- 恢复后自动续跑：恢复只重建现场，绝不重新请求模型或执行副作用。
- 把 PLAN 过滤放在审批层：模型请求的工具先经过模式过滤，返回结构化 unavailable 结果。
- 停止原因丢失：取消、错误和上限都写入 run 终态，UI 从持久化数据恢复。

## 7. 延伸与边界

本课模型仍没有系统提示，模型只能从对话猜规则。结构化系统提示、缓存和请求级提醒在第 04 课补齐。

## 实现快照与设计决策

> 以下为本课（s03）完成时点的实现快照；后续课次可能已替换或扩展对应实现。

### 阶段结果

s03 把 s02 控制器内固定的两阶段工具流程替换为独立异步事件驱动的 Agent 系统。用户只发送一次任务，系统便持续执行模型迭代、工具调度、结果回写与再次判断，直到自然完成、达到 20 轮上限、连续三轮全未知工具、用户取消或模型流失败。

每次模型请求对应一条独立助手消息。纯工具响应也会保存空正文消息及其工具卡片；每次迭代和整个 Agent 回合分别保存 Token 用量。

### 核心结构

- `src/agent/runner.ts` 是唯一循环入口，维护迭代、累计用量、未知工具计数和停止语义。
- `src/agent/stream-collector.ts` 单次消费 Provider 流，实时产生文本、思考、工具参数与用量事件，同时返回完整响应。
- `src/agent/safety-batch-scheduler.ts` 并发执行连续读取段，并让每个写入或命令形成逐项审批的串行屏障。
- `src/agent/context.ts` 保持 user、assistant tool call、tool result 的严格协议顺序。
- `src/chat/agent-event-projector.ts` 顺序写盘并投影 `AppState`，其事件背压保证工具开始前迭代与调用已持久化。
- `src/chat/agent-controller.ts` 只负责命令、会话、启动、取消与事件消费；`controller.ts` 保留 s02 手写实现作状态留痕并导出新控制器。

### Plan Mode

`/plan` 精确匹配且不请求模型。PLAN 会话只向模型公开 `read_file`、`find_files`、`search_text`；即使模型直接请求已注册的写入或命令，也会在审批前返回 `tool_unavailable_in_mode`。最近自然完成的计划按会话保存。

`/do` 切回 DO，历史仍显示 `/do`，但当前模型请求把它规范化为“根据当前会话中的最近计划立即执行”。无计划时不会创建 Agent 回合或请求模型。

### 存储与恢复

数据库版本 3 新增 `agent_runs`，并为会话、消息和工具记录增加模式、计划、回合、迭代和原始参数字段。旧会话默认 DO，旧记录的 Agent 关联保持空值。启动时未完成回合、流式消息和工具调用统一标记中断，不自动请求模型、重新审批或再次执行副作用。

### Provider 与安全边界

三个 Provider 都从同一 `ModelContextItem[]` 生成任意多轮协议历史，不启用 SDK 自动工具循环。工作区路径、UTF-8、超时、结果大小和命令限制继续复用 s02；只读并发不跨越副作用屏障，写入和命令仍逐项 `Y/N`。

### 2026-08-23 真实验收与收尾决定

使用已配置的 DeepSeek Anthropic 兼容 profile 完成了真实终端验收：PLAN 只读、`/do` 执行、写入和命令审批、拒绝后自动续跑、命令失败后调整、模型流取消、审批取消、运行中命令取消、取消后恢复发送、会话模式隔离与重启恢复均符合预期。测试用文件位于一次性工作区，未批准或已取消的写入均没有发生。

验收时发现重启和切换会话会把状态栏 Token 清零，同时可能沿用前一会话停止原因。`agent-controller.ts` 现从持久化消息和 `agent_runs` 恢复最近一次及累计用量、停止原因，并新增集成回归测试。

s01/s02 的请求兼容字段和 `LegacyChatController` 按用户“保留每个阶段代码”的要求继续存在。它们用于状态留痕和旧测试回归，生产组合根只使用 `AgentRunner`，因此这不是 s03 的未完成清理项。

阶段结论为 **s03 基本完成**。边界是：本次只真实验证了 DeepSeek 的 Anthropic 兼容端点；官方 Anthropic、OpenAI Responses 和 OpenAI Chat 三个原生端点尚未分别实测，不能声称供应商矩阵全部完成。
